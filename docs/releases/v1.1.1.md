## Deep Defense 1.1.1

Two passes over the program since 1.1.0. The first went down a list — memory, timing,
what a failed write leaves behind. The second read the program the way it is used:
every screen, every way out of it, every error path. Both found things, and the
second found more.

Nothing here changes the vault format. Vaults from 1.0.0 and 1.1.0 open as they are.

### A CONTAINER COULD END UP WITH NO PASSWORD THAT OPENED IT

A master-password change in container mode has three steps, and is built so that
stopping between any two of them leaves one of the two passwords working. The unlock
then undid that. It tidied away the spare key wrapping as soon as the volume opened —
before trying the vault inside. Type the password the vault had not taken, and it kept
the wrapping for that one and deleted the wrapping for the password the vault did
take: one password for the volume, the other for the vault, neither for both. The
tidying now waits for the vault to open.

The volume was also created with PIM 0 whatever the settings file said, and mounted
with the configured one, so a container made with a PIM configured never opened. And a
mount that VeraCrypt itself reported as failed still waited 45 seconds for the drive to
appear; it is given five.

### A HIDDEN VAULT COULD BE MADE WHERE NOTHING WOULD EVER OPEN IT

An unlock opens whichever slot answers first, and only that one. Three paths led to a
hidden vault no password could reach: creating it under the decoy's own password,
which the settings screen meant to catch and checked the wrong slot for; changing
either vault's password to the other's; and creating one inside a VeraCrypt container,
whose volume opens only for the master password. All three are refused now, and the
container case is explained in Settings rather than offered.

That screen's check also ran a full Argon2id derivation on every frame while anything
was typed, which froze the window. The vault answers once, when the button is pressed.

### EVERY CHANGE IS SAVED OR TAKEN BACK

A save can fail — a full disk, a memory stick pulled out — and several screens left
the vault in memory holding a change the disk did not have. An attachment that would
not save stayed in the list and counted against the slot on every save after it. A
deleted entry whose save failed was gone from the screen and present in the file. An
import too large for the slot made every later save fail until each imported entry was
deleted by hand. An edit that failed to save could not be saved again: the second
attempt was refused as "no such entry".

Every change now goes through one place, which saves it or puts the data back exactly
as it was. A change that turns out to change nothing is not saved at all, so pressing
Save on an entry that was only looked at no longer pushes a real backup off the end of
the row of five.

### NOTHING TYPED IS THROWN AWAY WITHOUT ASKING

A click on another entry, the arrow keys, "+", Ctrl+N, Esc, the lock button and
closing the window each dropped the editor as it stood. They ask now — save, discard,
or keep editing — and only when saving would change something. Ctrl+S, which the Save
button advertises, saved everything except the entry being edited; it saves that too.
The idle timer and the screen lock still do not ask: nobody is there to answer.

### A LOCK FORGETS EVERYTHING, AND SAYS WHAT WENT WRONG

Locking dropped the vault and kept the rest. An auto-type countdown started before the
lock finished after it and typed the password into whatever had focus. The recovery
pieces and every password half-typed into Settings stayed in memory, filled in, for
whoever unlocked next. Pieces pasted on the lock screen stayed for as long as the
program ran. All of it goes with the lock.

A save that failed on the way out is now said on the lock screen. The idle timer used
to put "locked automatically" over it.

### SECRETS ARE WIPED WHERE THEY USED TO BE FREED

Memory holding a secret was unlocked before it was wiped, so the page could be written
to the page file in between; Argon2's working memory, which the key is a hash of, was
freed as it was. Both are wiped first now. The vault is serialised once, into memory
that wipes itself, where there used to be several plaintext copies of every password
on the way to disk. The interface, the clipboard read-back, the keystrokes sent by
auto-type, the strength estimate and the recovery pieces as text all made copies that
were freed unwiped, and no longer do.

### UNLOCK TIME NO LONGER NAMES THE SLOT

Opening stopped at the first slot that answered, so the decoy's unlock took one
Argon2id pass and the hidden vault's took two: a stopwatch could tell which slot a
password belonged to, and that a second one was in use. Every slot is tried every
time.

### A FAILED WRITE LEAVES THINGS AS THEY WERE

Each failure point of a save, a restore and a mirror copy now has a test that makes it
fail there. They found that the backups moved along before the new file was written,
so a save that then failed had already pushed the oldest backup out; and that a failed
password change left the vault in memory under the new key and the disk under the old.

### THE CLIPBOARD IS CLEARED EVEN WHEN IT IS BUSY

One failed attempt to open the clipboard when the timer fired was the end of it:
nothing tried again, and the password stayed. Another program holding the clipboard
for a moment is ordinary on Windows, so it is tried ten times over a second.

### ERRORS IN YOUR OWN LANGUAGE

What the program says when it will not or cannot do something was written once, in
English, and shown as it was on a Russian screen. Seventy of those are now said in
both languages. Most had also gone out under the lead-in "Unrecognised vault format:",
which is how auto-type refusing its own window came to be described as a format error.

### SMALLER THINGS

- A two-factor secret typed with a letter from another alphabet was accepted — "Ł"
  read as "A" — and produced codes, the wrong ones.
- A CSV import trimmed passwords, so one that began or ended with a space came in as a
  different password.
- The "old password" warning measured from the last edit of any kind; a typo fixed in
  the notes made a password from years ago look new. Entries now keep the date their
  password was set.
- A second import of leaked passwords went into a filter sized for the first. A short
  list followed by a long one reported every password as leaked, the master password
  on the setup screen included.
- A settings file that would not parse was reported, and then overwritten by the
  defaults at the first change. It is moved aside under a dated name instead.
- Going back to Setup and choosing "Open existing" saved an empty keyfile list over
  the configured one. Rebuilding the file ignored keyfiles altogether, so with one in
  use the work factor could not be changed.
- A rename that only changed capitals was skipped and reported as saved. Two
  attachments with one name could not be told apart. A tag filter outlived its tag.
- Recovery pieces from two different sets were counted together as enough, and then
  refused. A piece written over several lines was not recognised.
- Auto-type typed when no window was in front. A keyfile was read into memory whole.
  A path containing "{}" garbled the message that named it.
- The generator's rejection limit kept two values too many, so the first two
  characters of most alphabets were a hair more likely than the rest.
- The search box, the notes, the two-factor secret and both halves of every custom
  field were announced by a screen reader as "edit, blank".

426 tests — 417, and nine that draw the screens — up from 378 in 1.1.0.

### WHAT WAS NOT CHECKED

The machine this is written on cannot run the program, so everything above was
verified by tests in CI and by the screens CI draws. The new question on the lock
button and on closing the window is tested as logic; nobody has clicked through it.
The VeraCrypt changes are tested as far as the command lines, as before.

## Install

Download `deep-defense.exe` and run it. That is the whole procedure — no installer,
no administrator rights, no runtime to fetch.

**Check the fingerprint before running it:**

```powershell
(Get-FileHash -Algorithm SHA256 .\deep-defense.exe).Hash
```

```
{{SHA256}}
```

A swapped executable is the end of everything this program protects — it would
simply read the password as you type it. There is no signing certificate here, so a
fingerprint recorded at build time is the next best thing. It is not a defence
against someone who replaces both the file and the fingerprint; it turns "is this
the file that was built?" into a question with an answer.

Built from `{{COMMIT}}` by the release workflow, Rust 1.98, target
`x86_64-pc-windows-gnu`. Rust builds are not reproducible byte for byte, so a build
of your own from this tag will hash differently — build it yourself and trust that
instead, if you prefer.

Going back to 1.1.0 afterwards works, with two things to know. The date a password
was set is new; 1.1.0 ignores it and drops it when it saves. And a second imported
list of leaked passwords is stored after the first in the same file, which 1.1.0 does
not read — it carries on with the list built into the program.

## Known limits

Eighteen of them are listed in the README, with the reason for each. The first is
still the one worth repeating: **this has not been audited.** One author, no
external review. What can be done short of that has been done, and `docs/REVIEW.md`
is there to make the rest cheap.

Found a security problem? [Report it privately](https://github.com/N0deZ3r0/deep-defense/security/advisories/new)
rather than in a public issue.
